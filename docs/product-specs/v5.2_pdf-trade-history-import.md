# v5.2 PDF 거래내역 업로드 Product Spec

- 작성일: 2026-08-26
- 상태: 현재 구현 기준
- 기준 문서: [v2.0 코인미러 PRD](../v2.0_coinmirror_product_prd.md), [v5.0 스코어 시스템 & 온보딩 설문](v5.0_score-system-and-onboarding-survey.md)

## 1. 결정 배경

업비트 고객센터에서 발급받는 거래내역은 이메일 첨부 PDF로 제공될 수 있다. 따라서 MVP 업로드 UX는 CSV 전용이 아니라 **PDF/CSV 거래내역 업로드**를 기본으로 다룬다.

## 2. 지원 범위

| 항목            | 현재 기준                                                                                       |
| --------------- | ----------------------------------------------------------------------------------------------- |
| 포맷            | 업비트 고객센터 PDF, 업비트 KRW CSV                                                             |
| PDF 암호        | 사용자가 앱에서 비밀번호를 입력한다. 입력값은 저장하거나 전송하지 않음                          |
| 암호 제거본     | **권장하지 않는다.** `인쇄 → PDF로 저장`은 텍스트 레이어를 파괴한다 (§4.1)                      |
| 추출            | PDF.js 텍스트 레이어 추출. 텍스트가 0자면 **명시적 실패**로 처리 (§4.2). OCR은 후속 범위        |
| 파싱 대상       | `매수`/`매도`인 `KRW-*` 거래 행만 `RawExecution`으로 변환                                       |
| 제외 대상       | 입금, 출금, 예치금 이용료, 지갑주소/상대방정보                                                  |
| 공통 파이프라인 | `RawExecution[]` → 30분 Order 병합 → FIFO RoundTrip → 파생 시계열 → F1/F3/F6/F8 → 투자거울 타입 |

## 3. 업비트 PDF row 패턴

텍스트 추출 후 아래 두 줄 조합을 1개 거래로 인식한다. 실제 개인정보, 발급번호, 지갑주소는 저장하거나 테스트 fixture에 넣지 않는다.

```text
번호
YYYY-MM-DD 매수|매도 KRW-자산 수량 자산 수수료 KRW
HH:mm:ss 거래단가 KRW 거래금액 KRW 정산금액 KRW
```

## 4. 실제 샘플 스모크 결과

2026-08-26 실제 업비트 고객센터 PDF **원본(암호 걸린 텍스트 PDF)** 을 미커밋 상태로 검증했다. 비밀번호와 원문 개인정보는 코드/문서에 남기지 않는다.

- PDF.js 텍스트 추출 성공
- 정상 매수/매도 row: 304건
- 오류 row: 0건
- 제외 row: 50건
- 기간: 2025.08.26 ~ 2026.08.24 KST
- 거래 자산 수: 16개
- 병합 후 Order: 226건
- FIFO RoundTrip: 107건
- F1/F3/F6/F8 모두 측정됨

### 4.1 ⚠️ 암호 제거본(인쇄 → PDF로 저장)은 파싱 불가

2026-08-27 같은 거래내역서의 암호 제거본을 검증한 결과, **텍스트가 한 글자도 추출되지 않았다.**

| | 원본 (암호 O) | 인쇄 → PDF 저장본 (암호 X) |
| --- | --- | --- |
| 크기 | 203 KB | 8.6 MB |
| 폰트 참조 | 25개 | **0개** |
| JPEG 이미지 | 0장 | **35장** |
| 텍스트 출력 연산자 (Tj/TJ) | 있음 | **0개** |
| 추출 문자수 | 정상 | **0자** |

`인쇄 → PDF로 저장`이 글자를 이미지로 래스터화한다. 따라서:

1. 이 우회 경로를 **제품에서 권장하지 않는다.** 안내 문구와 버튼을 제거했다.
2. 사용자에게는 **원본 업로드 + 앱 내 비밀번호 입력**이 유일한 정상 경로다.
3. 보안상으로도 원본이 낫다. 암호 제거본은 보호가 벗겨진 거래내역서가 기기에 남는다. 사용자는 더 안전하다고 느끼지만 실제로는 반대다. 이 점을 업로드 화면에서 설명한다.

### 4.2 이미지 PDF 감지 규칙 (침묵 실패 금지)

텍스트 레이어가 없는 PDF를 빈 결과로 흘려보내면 `0건 · 오류 0건`이라는 침묵 실패가 된다. CSV 파서의 `emptyFailure` 원칙을 PDF에도 동일하게 적용한다.

| 단계 | 조건 | 동작 |
| --- | --- | --- |
| 추출 | 공백 제외 문자수 0 | `PdfNoTextLayerError(pageCount)` 발생 → 이미지 PDF 안내 |
| 파싱 | 텍스트는 있으나 매수/매도 행 0건 | 업비트 서식 여부를 판별해 사유가 다른 명시적 오류 반환 |
| 파싱 | 업비트 서식이 아님 | `업비트 거래내역서 형식이 아닙니다` + 읽은 줄 수 |

`detectedAdapter`는 실제 체결을 하나라도 인식했을 때만 설정한다.

## 5. UX 문구 원칙

- 업로드 전 고객이 자료 형식을 직접 고르도록 `PDF 거래내역 올리기`와 `CSV 거래내역 올리기`를 별도 선택지로 표시한다.
- 기본 안내는 “업비트 고객센터에서 받은 PDF가 가장 일반적인 경로”라고 설명하되, CSV 보유 고객도 선택할 수 있게 한다.
- 파싱 미리보기는 `PDF 거래내역` 또는 `CSV 거래내역`으로 출처를 구분한다.
- 암호화 PDF는 **앱 내 비밀번호 입력**을 안내한다. 암호 제거본 업로드는 안내하지 않는다 (§4.1).
- 비밀번호 입력이 부담스러운 고객에게는 **우회 절차 대신 신뢰 근거**를 설명한다.
  - 이 비밀번호는 거래소 계정 암호가 아니라 PDF 파일 하나를 여는 암호다.
  - 기기 안에서 파일을 여는 데만 쓰고 저장하거나 서버로 보내지 않는다.
  - 암호를 지운 파일이 오히려 위험하다. 보호가 벗겨진 거래내역서가 기기에 남는다.
- 이미지 PDF를 올린 경우 쪽수와 원인을 밝히고 원본 업로드를 안내한다. `0건`으로 끝내지 않는다.
- 원본 파일과 PDF 비밀번호는 서버로 전송하거나 저장하지 않는다고 명시한다.

## 6. 후속 과제

1. **OCR 지원 여부 판단** — 실제로 이미지 PDF를 올리는 사용자 비율을 본 뒤 결정한다. 현재 표본은 0명이다.
   - 이 제품에서 OCR은 위험하다. 표 한 행에 숫자가 5개(수량·수수료·단가·금액·정산금액)이고, 자릿수 하나를 잘못 읽어도 조용히 점수가 오염된다.
   - Local-First와도 충돌한다. 브라우저 OCR은 한글 표 정확도가 낮고, 서버 OCR은 원본 업로드를 요구한다.
   - 도입한다면 **검산 통과 행만 채택**하는 설계가 전제다: `거래수량 × 거래단가 ≈ 거래금액`, `거래금액 − 수수료 = 정산금액`. 통과하지 못한 행은 격리해 오류로 노출한다.
2. PDF.js 텍스트 추출이 레이아웃을 잃는 예외 PDF 샘플 추가 검증.
3. F2/F4/F5/F7/F9/F10의 실제 PDF/CSV 기반 계산 확장.
4. 암호 입력 UX를 `window.prompt` 임시 방식에서 정식 보안 입력 컴포넌트로 교체.
