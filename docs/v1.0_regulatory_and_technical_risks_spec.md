# v1.0 코인미러 규제 및 기술적 제약사항 대응 전략 명세서

- **작성일**: 2026-08-04 (2026-08-10 코인미러 기준으로 재작성)
- **대상 프로젝트**: 코인미러 (coinmirror) — 투자 행동 회고 웰니스 앱
- **문서 목적**: 서비스 구현 및 시장 출시 시 직면할 법적 규제(자본시장법, 가상자산이용자보호법)와 기술적 병목(파일 파싱, 향후 API 연동 시 Rate Limit 등)을 정의하고 구체적인 대응 전략을 명시하여 개발 마찰을 최소화함.
- **참고**: 이 문서는 원래 자매 프로젝트 "Alpha Pulse"(실시간 거래소 API 연동 기반 매매 감사 플랫폼)용으로 작성됐던 문서를 코인미러의 실제 아키텍처(CSV/PDF-First, Batch-First, 실시간 서버 연동 없음)에 맞게 재작성한 것이다. 원본은 코인미러와 다른 전제(상시 API 연동, 웹소켓 실시간 알림)를 깔고 있었으므로 그대로 참조하지 말 것.

## 1. 법적 및 규제 제약사항 대응 전략 (Regulatory Risk Mitigations)

### 1.1 자본시장법상 '미인가 투자자문' 지뢰밭 우회

- **리스크 정의**: AI 피드백 엔진이 사용자에게 특정 가상자산에 대한 미래 가격 예측, 매수/매도 시점 추천, 포트폴리오 비중 조정 지시 등을 제공할 경우, 자본시장법상 **유사투자자문업 및 미인가 투자자문업** 규제 위반으로 형사 처벌 대상이 됨.
- **대응 전략 (Backward-looking Audit / Mirroring Principle)**:
  1. **사후 감사 포지셔닝**: 모든 분석은 미래 예측이 아니라 **이미 체결이 완료된 과거 거래 데이터**에 대한 사후 분석·피드백으로 한정한다.
  2. **행동 데이터 초점**: "어떤 코인을 사야 하는가"가 아니라 "진입 당시 사용자가 사전에 기록한 목표가/손절가/근거 태그 대비 실제 실행이 어땠는가"에 집중한다. (`docs/v1.0_expo_app_development_prd.md` §6.4, §10 참고)
  3. **면책 고지(Disclaimer) 시스템 내재화**: 리포트 및 스코어 상세 하단에 "본 서비스는 과거 거래 데이터와 사용자가 직접 입력한 기록을 기반으로 투자 습관을 요약하는 회고 도구이며, 투자 자문이 아닙니다" 문구를 강제 결합한다.
  4. **금지 표현 필터**: `docs/v1.0_expo_app_development_prd.md` §10.3의 금지 표현 목록(`지금 사세요`, `비중을 줄이세요` 등)을 AI 생성 문장 후처리 단계에서 기계적으로 검사한다.

### 1.2 가상자산이용자보호법(2024년 7월 시행) 대응

- **리스크 정의**: 자금 예치, 매매 주선, 신용 공여 등 가상자산 사업자(VASP) 라이선스가 필요한 행위로 오인될 경우 컴플라이언스 비용을 감당할 수 없음.
- **대응 전략 (Zero-Execution, Read-Only 원칙)**:
  1. **비보관(Non-Custodial)**: 사용자의 가상자산·원화 예수금을 단 1원도 자체 시스템에 위탁·보관하지 않는다.
  2. **거래 집행 완전 배제**: MVP는 주문/출금 실행 기능 자체가 없다(CSV/PDF 업로드, 수동 입력만). Phase 7에서 거래소 API를 연동하더라도 **조회(Read-Only) 권한만** 요청하는 아키텍처로 제한한다 — 이 원칙은 향후에도 예외 없이 유지한다.

### 1.3 개인정보보호법 및 금융 프라이버시 리스크 방어

- **리스크 정의**: 거래 내역·평단가·손익 등은 사용자의 자산 규모를 유추할 수 있는 민감 금융 데이터다. 중앙 DB에 원본 그대로 쌓이면 유출 시 단일 실패점이 된다.
- **대응 전략 (Local-First & 최소 수집)**:
  1. **로컬 우선 저장**: 원본 거래 내역(Trade, JournalEntry)은 기기 로컬 DB(SQLite 등)에 우선 저장한다. 서버(Supabase) 전송은 사용자가 명시적으로 동의한 요약/집계 데이터부터 시작한다. (`docs/SECURITY.md`, PRD §8.2 참고)
  2. **API Key 저장 원칙(Phase 7 대비)**: 향후 거래소 Read-Only API Key를 지원할 경우, 평문 저장을 금지하고 `expo-secure-store` 또는 서버 측 암호화(KMS/pgcrypto)만 허용한다.
  3. **서버 데이터 비식별화**: 통계·AI 분석용으로 서버에 전송되는 데이터는 이메일·이름 등 식별 정보를 제거한 집계 형태를 우선한다.

## 2. 기술적 제약사항 대응 전략 (Technical Risk Mitigations)

### 2.1 CSV/PDF 파싱 안정성 (MVP 핵심 병목)

- **리스크 정의**: 거래소마다 CSV 컬럼 구조가 다르고, PDF 거래내역서는 텍스트형/스캔형이 섞여 있어 파싱 실패 시 사용자가 온보딩 초기에 이탈한다.
- **대응 전략**:
  1. **거래소별 매핑 테이블**: 업비트/빗썸 CSV 컬럼 매핑을 우선 완성하고, 기타 거래소는 `직접 매핑` 또는 `준비 중`으로 명시한다. (PRD §6.3)
  2. **PDF는 서버/Edge Function에서 텍스트 추출**: 모바일 로컬 파싱보다 서버 파싱을 권장한다. 스캔형(이미지) PDF는 MVP에서 `인식 불가` 처리하고 수동 입력으로 유도한다 — 잘못된 자동 인식이 만드는 오차가 스코어 신뢰도를 해친다.
  3. **미리보기 + 오류 행 표시**: 가져오기 확정 전 반드시 파싱 결과를 사용자에게 보여주고, 실패한 행만 제외하고 가져올 수 있게 한다.

### 2.2 원시 체결 데이터(Raw Ledger)의 노이즈 정규화

- **리스크 정의**: 분할 체결(한 주문이 여러 번에 나눠 체결), 에어드랍 유입, 수수료 공제 시점 차이, 코인 간 직접 스왑 등으로 인해 평단가·수익률 계산에 오차가 발생한다.
- **대응 전략**:
  1. **체결 병합 규칙**: 동일 타임스탬프 근방·동일 주문 ID의 다중 체결을 하나의 가중평균 체결 건으로 정규화한다.
  2. **수수료 분리 표준화**: 수수료를 손익과 분리해 별도 지표(`docs/v1.0_personalized_score_system_spec.md` S16 수수료 효율)로 다룬다.
  3. **KRW 마켓 우선**: 국내 거래소(업비트/빗썸) 원화 마켓 정규화 규칙을 먼저 완성한 뒤, 글로벌 거래소(USDT 마켓)로 확장한다.

### 2.3 실시간 알림/웹소켓 — MVP 범위 아님 (향후 확장 검토)

> 이 섹션은 원본(Alpha Pulse) 문서의 "실시간 모니터링" 전략을 그대로 가져온 것이 아니라, **코인미러는 이 기능을 채택하지 않는다는 결정을 명시하기 위해** 남겨둔다.

- **원본 리스크 정의(참고용)**: 매수 시점에 실시간으로 스코어/쿨다운 알림을 주려면 웹소켓 상시 연결 또는 폴링이 필요하고, 유저 규모에 비례해 인프라 비용이 늘어난다.
- **코인미러의 결정**: `docs/v6.0_cto_business_proposal.md` §1~2에서 이미 실시간 서버 연동을 배제하고 **Batch-First**(일간/주간 리포트 중심)로 방향을 확정했다. 따라서:
  1. 웹소켓/상시 폴링 인프라는 만들지 않는다.
  2. "실시간 쿨다운 알림" 같은 기능이 필요해지면, 이 섹션을 갱신하고 별도 리스크 재평가를 거친 뒤 `docs/exec-plans/`에 계획을 세운다.
  3. 현재 알림은 주간 리포트 발행 시점의 배치 푸시/Telegram 알림 정도로 제한한다.

### 2.4 거래소 API Rate Limit — Phase 7(Read-Only API 연동) 대비 참고

- **리스크 정의**: Phase 7에서 업비트/빗썸/바이낸스 Read-Only API를 붙이면, 거래소별 초당 호출 제한을 넘길 경우 IP 밴이 발생할 수 있다.
- **대응 전략(현재는 참고, 구현은 Phase 7에서)**:
  1. **CSV/PDF가 여전히 기본값**: API 연동은 CSV/PDF 입력을 대체하지 않고 보완하는 선택지로 설계한다. API가 실패해도 CSV/PDF 경로는 항상 동작해야 한다.
  2. **CCXT 표준화**: 거래소별 API 스펙 차이를 CCXT로 흡수하고, 호출 큐를 둔다.
  3. **클라이언트 사이드 폴링 지양**: 모바일 앱에서 각 거래소에 직접 폴링하기보다, 서버(Edge Function)에서 배치로 동기화해 Rate Limit 관리와 API Key 노출 범위를 좁힌다.

## 3. 리스크 통제 매트릭스 (코인미러 기준)

| 투자자문법 위반 (조언처럼 보이는 문구) | 상 | **높음 (MVP부터 해당)** | 금지 표현 필터, 사후 감사형 카피 가이드 | 리포트/스코어 문구에서 미래 지향적 조언·추천 키워드 배제 검사 |
